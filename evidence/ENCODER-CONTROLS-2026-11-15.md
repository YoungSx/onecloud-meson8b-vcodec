## P0 基线工具与方法

`tests/encode-test.c` 生成确定性的 static/motion/scene/noise 源，逐帧输出
字节数、标志和 OUTPUT QBUF 到 CAPTURE DQBUF 的延迟；`-g` 在任何主机上生成
相同参考，经管道送入 FFmpeg 计算 PSNR，不在目标机保存原始视频。
`scripts/encode-baseline.py` 在 SSH 会话之外运行，记录进程 CPU、相对运行前
空闲速率的系统 CPU 增量（含 kworker）、墙钟、平均与 1 秒窗口峰值码率、延迟
中位数/p95/最大值、最低 MemAvailable/CmaFree、温度和逐帧 PSNR。每种情况
运行三次。上一版脚本把校验解码的耗时记作编码耗时，那份报告作废。

注意：同一输入在有运动时码流不逐字节一致。720p motion 连续三次从第 27 帧
开始出现 1 字节级差异；同时运行 32 MiB 内存拷贝负载时第 3–4 帧即开始分歧
（[determinism](encoder-2026-11-15/determinism-720p-motion.log)，第 4、5 次为
加负载）。运动搜索结果随 DRAM 时序变化，PSNR 不变。逐字节对比只能用于
static 内容；motion/scene 用 PSNR 与码率分布比较。

## P0：已安装模块的基线

1080p30×150 帧，固定 QP 26（中位数，[原始数据](encoder-2026-11-15/baseline-bd1cb79-main.json)）：

| 内容 | 码率 kbit/s | PSNR Y 平均/最低 | 延迟中位/p95 ms | 客户端 fps |
| --- | --- | --- | --- | --- |
| static | 1970 | 40.37 / 40.37 | 17.9 / 34.0 | 23.8 |
| motion | 14568 | 39.70 / 38.45 | 20.1 / 33.5 | 22.1 |
| scene | 21283 | 38.24 / 34.66 | 20.2 / 35.7 | 21.8 |

同步客户端每帧 3.2–3.8 s/150 帧的进程 CPU 主要是生成与拷贝测试源；
系统 CPU 增量比进程 CPU 多约 0.7–1.2 s，即编码 work（输入暂存拷贝、寄存器
配置、码流拷贝）每帧约 5–8 ms。FFmpeg testsrc2 1080p 150 帧：
`h264_v4l2m2m -b:v 0` 墙钟 4.6 s、进程 CPU 6.0 s；`libx264 ultrafast`
墙钟 7.9 s、进程 CPU 24.1 s，CPU 降低 75%，与 2026-11-13 记录一致。

基线暴露了三个缺陷：

- **CBR 码流解码错误。** 旧驱动 CBR 下 PSNR 只有 10–25 dB，且平均码率
  超出目标 1–4 倍。`trace_headers` 显示 PPS `pic_init_qp_minus26=0`、所有
  slice `slice_qp_delta=0`：驱动每帧把 QP 写进 QPPICTURE，解码端始终按 QP 26
  重建。修复为常量 26（`f07f82d`）后，I/P QP 30/36 的 slice_qp_delta 为 4/10。
- **QP 范围控件死锁。** 设置非默认 MIN_QP/MAX_QP 的客户端在
  `find_ref_lock` 进入 D 状态，编码器一直占用。本次测试曾触发，已用一次性
  恢复模块释放该互斥量，进程随挂起的 SIGKILL 退出；没有重启。修复为
  `f50b452`。FFmpeg 只发送默认值 0/51，因此此前未触发。
- **超过 1 MiB 的单帧。** 带防护区的探测模块确认 VLC 停在缓冲末尾
  （`VLC_VB_WR_PTR` 等于末尾，`VLC_VB_LEFT=5`），不会越界写，但微码一直等待，
  驱动 5 秒后才超时（[probe](encoder-2026-11-15/overflow-probe.log)）。
  `53cd705` 改为约 150 ms 内报 `-ENOSPC`，返回错误缓冲并令下一帧为 IDR。
  1080p 全频带噪声在 QP 40–44 仍超出 1 MiB，属于病态内容。

## P1：控件行为

[功能检查](encoder-2026-11-15/p1-functional.log)（候选 `b9445d88`）全部通过：
I/P QP、MIN/MAX_QP 不再死锁且按簇校验（单独设置 min>max 拒绝，同一事务
从 (0,20) 改为 (30,40) 接受）、HEADER_MODE 只接受 JOINED、GOP 0 只有首帧
IDR、强制关键帧、GOP 30 帧号回绕后可完整解码、码率目标与运行中改目标、
30000/1001 帧率、RC 关闭时固定 QP、FFmpeg `-b:v 0`/默认/`-b:v 2M`/
`-qmin 20 -qmax 30`/`-g 0`/`-force_key_frames` 回归、JPEG 回归和连续会话。

本机微码只在 SPS 中写底部裁剪、不写 VUI，SPS 为 Baseline、level 4.0、
`max_num_ref_frames=1`。驱动不在主机端补写 VUI。

## P1：码率控制

微码按主机给出的 QP 量化，没有自带码率控制。固定 QP 扫描
（[640x360](encoder-2026-11-15/qp-sweep-640x360.txt)、
[720p](encoder-2026-11-15/p2/qp-sweep-1280x720.txt)）显示 QP 32 以上码率不再
下降，static/scene 内容反而上升：720p QP 32/36/40 时 static 为
766/1063/1738 kbit/s、scene 为 7478/8001/7587 kbit/s，PSNR 下降 6 dB。原因是
强制跳过 SAD 阈值不随 QP 变化；按 QP 缩放阈值的试验对 scene 在 QP 38/51
更差，未采用。控制器的 P 帧 QP 上限先取 40，比较后改为 32（`4d7ba5b`）；
固定 QP 不受限。

同目标对比（[旧控制器](encoder-2026-11-15/compare-legacy-rc.json) /
[新控制器](encoder-2026-11-15/compare-leaky-bucket.json)，均含 QPPICTURE 修复，
目标为同一情况固定 QP 26 码率的 0.85/1.5/2.5 倍，三次中位数）：

| 1080p 情况 | 目标 | 旧：误差 / 1 s 峰值 / PSNR 平均·最低 | 新：误差 / 1 s 峰值 / PSNR 平均·最低 |
| --- | --- | --- | --- |
| motion ×0.85 | 12382 | +0.3% / 15076 / 34.50·23.30 | +0.6% / 12942 / 38.97·37.45 |
| motion ×1.5 | 21851 | −6.0% / 27427 / 37.48·23.44 | +0.2% / 22943 / 39.98·39.00 |
| scene ×1.5 | 31924 | −2.2% / 44086 / 35.89·22.21 | +1.0% / 39092 / 39.28·34.84 |
| scene ×2.5 | 53207 | −0.4% / 68518 / 39.69·30.11 | −0.0% / 61768 / 40.52·37.34 |
| static ×1.5 | 2955 | +187% / 9516 / 30.07·23.42 | +33% / 5100 / 37.26·32.26 |

上表新控制器一列为上限 40 的结果。motion/scene 在三种尺寸、三种目标下平均
误差均在 ±1.8% 以内，旧控制器为 −6.8%～+1.8%；1 秒峰值和最差帧质量均明显
改善。固定 QP 路径两个模块结果一致。三种 4:2:0 输入格式在 static 内容上码流
逐字节相同（[formats](encoder-2026-11-15/compare-formats.json)）。比较期间
dmesg 无告警。

上限改为 32 后重测 720p/1080p（[ceiling32](encoder-2026-11-15/p2/compare-ceiling32.json)）：

| 1080p 情况 | 目标 | 上限 40：误差 / PSNR 平均·最低 | 上限 32：误差 / PSNR 平均·最低 |
| --- | --- | --- | --- |
| static ×0.85 | 1675 | +124% / 33.59·32.17 | +32% / 37.25·34.06 |
| static ×1.5 | 2955 | +33% / 37.26·32.26 | +15% / 40.44·38.71 |
| motion ×0.85 | 12382 | +0.6% / 38.97·37.45 | +0.6% / 38.97·37.45 |

720p static ×0.85 从 +110% 降到 +28%。scene 的低目标因上限略多超出，但
平均和最差帧质量都更高。

## 限制

- 低于 QP 32 码率的目标不可达，控制器停在 QP 32；static 内容的低目标仍超出。
- 场景切换的第一帧无法预测，会造成单帧超额；随后一帧即按新复杂度调整。
- 码流无 VUI，色彩与帧率需由封装层携带。
