# MPEG-4 帧尾逐帧定位（2026-11-16）

修正 [drain-eos.md](../p6-2026-11-15/drain-eos.md) 里"MPEG-4 起始码方案已排除、
尾两帧永久缺失"的结论。此前只用**交付帧数**判断，无法区分"补回来的那帧是缺失
图像"还是"陈旧重复"，因此把有效方案一起判掉了。这次逐帧对齐到软解参考，结论
相反：**两帧可以拿回，且已在硬件上验证。**

## 方法

1. 参考流 `base2.m4v`（md5 `02eab497726be0633a58b962e4198d14`，90 个 VOP，
   3 个 I + 87 个 P，软解 90 帧）按 `scripts/m4v-tail-hash.sh` 的变体在末尾
   追加不同尾部，逐个送硬解并导出帧。
2. 每帧为 `196608` B = luma `131072`（`ALIGN(ALIGN(320,64)*ALIGN(240,64),64K)`）
   + chroma `65536`，即一整帧 canvas 对齐 NV12M，所以 `dump / 196608` 就是
   真实图像数；客户端打印的 `EOS frames=` 是出队次数（base 报 92），会重复
   计入零载荷出队，不能当帧数。
3. 硬解与软解 MPEG-4 **不逐字节相同**（IDCT 实现差异，与此前验收用 PSNR 而非
   md5 的原因一致），因此不比对哈希，改为每帧取可见区 8×8 网格的平均亮度
   （64 个数）做签名，再按顺序与软解逐帧匹配，容差 2。`scripts/m4v-frame-compare.py`
   的 `--self-test` 校验 canvas 几何，已并入 `make test`。

## 结果

`delta 0` 表示该帧的 64 格平均亮度与对应软解帧完全相同。所有变体的匹配帧
**全部** `delta 0`、全部按顺序一一对应，没有任何一帧落到错误的参考帧上。

| 变体 | 尾部 | 交付帧 | 对齐到软解 ref | 缺失 |
| --- | --- | --- | --- | --- |
| base | 无 | 88 | 0–87 | 88, 89 |
| last1 | 末幅编码 VOP ×1 | 89 | 0–88 | 89 |
| **last2** | 末幅编码 VOP ×2 | **90** | **0–89** | **无** |
| last1vos | VOP ×1 + 序列结束 | 89 | 0–88 | 89 |
| **last2vos** | VOP ×2 + 序列结束 | **90** | **0–89** | **无** |
| dup | 同 last2（原始 dup 流就是 base + 末幅 VOP ×2） | 90 | 0–89 | 无 |
| cvop1/2/3 | not-coded VOP（头 `10 60`）×1/2/3 | 89 | 0–88 | 89 |
| voscv | 序列结束 + not-coded VOP | 88 | 0–87 | 88, 89 |

软解对 `last2` 类流输出 92 帧，多出的 ref 90/91 是它自己把重复 VOP 再解一遍
产生的陈旧重复；硬件交付的 90 帧正好覆盖 0–89 这 90 幅真实图像，一幅不缺。

原始日志：[m4v-tail-hash.log](m4v-tail-hash.log)（六个变体，含每帧 64 格签名）。

## 机制

- **每追加一个完整编码图像起始，固件就完成一幅待决图像。** MPEG-4 固件在流结束
  时压着 2 幅（本流），所以要 2 个。
- not-coded VOP（`10 60`）只能释放 1 幅，之后多送无效（cvop1/2/3 都是 89）。
- **序列结束码之后的 VOP 被忽略**（voscv 只有 88），所以顺序必须是
  "先补齐 VOP、最后送序列结束码"；`last2vos` 证明这个顺序可行，尾帧不丢。
- 这与 MPEG-1/2 的差异（那边 1 个图像起始码就够）一致：待决深度取决于编码格式，
  不是通用常量。

## 驱动侧的现状与代价

驱动 drain 目前只送 `00 00 01 B1`（`vdec/codec_mpeg4.c:54`、`:187`），所以
MPEG-4 停在 88 帧。要按上面验证过的顺序补齐，驱动必须**保留输入流末尾那幅编码
VOP**：`esparser_queue_eos()` 只接受调用方给的字节，而 VIFIFO 里的数据已被消费，
唯一的来源是输入流本身。

这意味着要给 esparser 增加一个"每段输入送固件前先看一眼"的钩子，由 MPEG-4 侧
扫 `00 00 01 B6` 记住最后一个完整 VOP。风险点是 VOP 可能跨两个 OUTPUT buffer
（本次末幅 VOP 为 5184 B，客户端按起始码分块，恰好完整），跨块时截断的 VOP 会
让固件解出一幅坏图——比少两帧更糟。

因此本轮**不改驱动**：结论与验证顺序已固定在案，实现要连同"跨块 VOP 如何判定
不完整、宁可不补"一起做。在做到之前，MPEG-4 的对外声明仍是"尾两帧缺失"。

## 未覆盖

- 只有这一个 320x240、I/P 流的样本。B 帧、多视点、分辨率中途变化未测。
- 待决深度 2 是这个样本的值，没有验证是否随流特性变化；驱动若实现，补的 VOP
  数量不能硬编码为 2。
- 逐帧比较用的是 8×8 网格平均亮度，能识别"哪一幅"，不能替代像素级 PSNR 验收。
