## 目标与约束

优先提高编码控制的正确性、输入兼容性、CPU/内存效率和延迟，再扩大
解码兼容性与持续负载覆盖。当前目标保持 OneCloud 原 Linux 5.15.79-meson、
64 MiB CMA 和 WanOS 应用层，所有构建在外部机器完成。

使用 V4L2/vb2、DMA-BUF、时钟、canvas 与 PMU 的原生接口。新增功能有
明确硬件依据才暴露；控件接受成功必须对应实际行为。保留已验收包、
固件备份和完整回滚路径，不修改 `/boot`，不停止五项原有业务服务。
不能把 CPU/GPU 软件编码标成专用硬件编码。

## P0 — 先建立可信基线

复用现有 V4L2 客户端和测试脚本，补需要验证的控件、帧类型、头部/NAL、
输入格式与计时接口。当前脚本有实验目录假设，逐个改为显式参数，只保留
测试所需选项。先跑固定 QP 与已有 CBR，不先改变编码器算法。

样片覆盖静态画面、运动、噪声/纹理、场景切换，尺寸先用 320×240、720p、
1080p；输入先用现有 NV12/NV21/YUV420。参考帧与输出保持相同色彩契约。
裸流按源帧率重定时，避免 PSNR 比错帧。

记录完整输出帧数、解码质量、单帧大小、平均码率、1 秒窗口峰值码率，
以及 QBUF→DQBUF 延迟的中位/p95/最大值、吞吐、温度、CMA/内存峰值。
CPU 同时记录进程和系统级增量，包含 kworker；管理 SSH 不参与测量负载。
比较前保持输入、QP/目标码率、GOP 和负载一致，至少三次报告结果分布。

P0 完成条件：当前有效路径可重复通过内容和帧数检查，得到可用于前后
比较的基线；纠正已有 JSON/文档数字或测试方法矛盾，保留旧记录的日期。

## P1 — 编码控件与码率/质量

先核对 QP min/max、GOP、FORCE_KEY_FRAME、HEADER_MODE 的实际行为。
QP 范围用标准控件关系校验，动态设置与编码 work 同步；CBR 调节也遵守
用户 QP 范围。HEADER_MODE 收窄为实际支持的 joined-with-first-frame，
回归原 FFmpeg 的调用顺序。

在微码证据与码流测试支持下增加 I/P 帧 QP 控制。VUI 的色彩/帧率信息
先确认固件生成头部能否配置；没有接口时，不在 host 随意拼补 SPS。
不增加没有证据的 profile、CABAC、B 帧编码选项。

再改善当前累积码量调 QP：处理场景切换、长序列误差积累、目标码率调整
和控制状态重置。用有界状态和反馈，依据基线选择控制算法；不预先把 PID、
前瞻或重编码引入低内存管线。必要时支持标准的固定 QP/码率控制模式。

验收：有效/非法控件、运行中调整、I/P/IDR、头部、EOS 与新会话恢复；
同码率比较平均误差、窗口峰值、逐帧质量和 CPU/延迟。先要求默认路径
无回归，再证明改进；不承诺每帧严格限码，也不把不同码率 PSNR 当收益。

## P2 — 输入格式与颜色

按小批次增加 RGB24/RGBA32 和有厂商依据的 YUV422 布局，随后评估 YUV444。
先区分 V4L2 内存格式与 MFDIN 模式，核对 canvas/linear、RGB2YUV、下采样、
通道顺序、色彩矩阵/量程。输入 YUV422/444 不代表输出码流变成相同色度格式。

统一格式协商、stride、plane span、bytesused/data_offset 与边缘填充规则。
不能为了兼容单个 FFmpeg 强制其他标准客户端使用隐含布局。JPEG 保持
全量程输入契约，有限量程转换须明确，不静默改变已有输入。

验收：彩条、灰阶、纯色、边界图像及奇数/非对齐尺寸协商；逐格式比较
软件转换参考，确认颜色和可见尺寸。每批回归 AVC/JPEG 的现有三种输入
格式，非法布局返回错误而不越界或产生错误成功结果。

## P3 — 减少编码输入拷贝

P2 固定布局契约后，评估将连续、可 DMA 映射且满足 stride/plane span
要求的缓冲直接送 MFDIN。当前 encoder 使用 vmalloc vb2 并复制到内部
staging，仅接受 DMA-BUF 不等于直接 DMA，需核对 memops、attachment、
映射与 ownership。

先支持一种已验证 NV12 布局；不兼容布局使用明确的现有复制路径，扩展
其他格式逐个验证。保留原低 CMA 路径，不能为每个队列缓冲分配新的连续
帧导致并发预算倒退。CPU/DMA 同步、缓冲归还时机、STOP/STREAMOFF、失败
恢复和格式变更都按内核原生契约实现。

验收：MMAP 与 DMA-BUF、可兼容/不可兼容布局、完整帧内容、反复启停和
用户退出；1080p B 帧并发仍在原 64 MiB CMA 下工作。收益用端到端 CPU、
吞吐、延迟和内存确认，只减少一次复制不宣称端到端零拷贝。

## P4 — 多分片与低延迟

先用厂商 FIXED_SLICE_CFG/rows_per_slice 实现有证据的分片模式，对应标准
V4L2 控件只暴露可验证设置。检查 IDR/P 帧分片数量、码流解码和头部行为。
分片后的 NAL 边界不自动意味着用户提前收到数据。

随后核对是否有 slice 完成中断、可靠字节边界和可持续写入/消费的缓冲
协议。仅在这些成立时开发提前交付，并使用标准接口；保持一帧 buffer
语义的客户端必须兼容。如果只有整帧完成，则交付多分片，明确不支持
逐片低延迟，不制造虚假的延迟选项。

验收：不同分片大小、I/P 帧、完整图像/时间戳、CAPTURE 回压、EOS、退出
恢复；分别报告整帧 QBUF→DQBUF 与有证据的首 slice 交付延迟。

## P5 — 解码输出与 GE2D 的可行性门槛

先根据 P0 和后续性能数据确定转换/拷贝耗时。已有 swap64 路径与 cropped
逐字节路径分别分析，不凭 CPU 高就直接增加新硬件驱动。

GE2D 先独立证明 YUV 输入、输出布局、字节序处理、色彩与共享资源生命周期。
现有主线格式路径不完整，厂商资料不足的环节先记录。一个小样片正确且
包含搬运/同步的净收益成立后，才接入缩放或颜色转换管线。

若不能处理 VDEC 字节序，GE2D 可限于已转换帧的缩放；不声称它消除了
前序 CPU 转换。解码 DMA-BUF 输出也需解决 shadow reference 生命周期，
独立于 P3 编码输入优化。验收包括原始帧哈希、裁剪、参考帧、EOS 与并发。

2026-11-15 完成：NEON 字拷贝把 1080p 转换从约 15 ms 降到 7–8 ms，裁剪
窗口按行有界拷贝；同时修正 canvas 尺寸与 HEVC 裁剪窗口复用。GE2D 在
meson8b 无节点、无 VDEC 字节序路径，不接入，结论与限制见
[P5 记录](../evidence/P5-DECODER-CONVERT-2026-11-15.md)。

## P6 — 兼容性、持续负载与发布

补齐已知 MPEG/VC-1 帧尾边界、MJPEG 色彩说明及 FFmpeg 分辨率切换问题的
最小复现。区分显示重复、码流损坏和真正丢帧，驱动与用户态根因分别修复；
不把所有错误统一归为 FFmpeg。

2026-11-15 进展：运行包升级、回滚演练与重启循环已实机验证（见
[p6-2026-11-15](../evidence/p6-2026-11-15/deploy.log)）；MPEG-4 帧尾边界
复现确认固件只在下一张图开始时才完成当前图，当前 drain 只送序列结束码，
因此最后 1–2 帧永不完成，补一个假图像起始码可恢复一帧、补两个可恢复两帧
但会多出陈旧缓冲（见 [compat.log](../evidence/p6-2026-11-15/compat.log)）。
进一步核查发现更前置的根因：`esparser_queue_eos()` 按 `len + 512` 分配，
而 `esparser_pad_buffer()` 会把小于 4 KiB 的负载补到 4096 字节再加 512 字节
搜索窗，两者矛盾，导致 4 字节序列结束码一律返回 `-ENOSPC`，调用方又不检查
返回值——自 243160b 起 MPEG/VC-1 的 drain 实际没有向固件写入任何内容；此外
原实现只写负载不写 padding，`000001ff` 终止码不写就不触发搜索中断。

修复后 MPEG-1/2 帧尾完整：90 帧参考流由 88 帧恢复到 90 帧并与软件参考逐
字节一致，150 帧 B 帧流返回全部 150 帧。MPEG-4 对追加 VOP 起始码无响应
（1/2/3 个都仍为 88 帧），尾两帧仍缺失，限制保留。VC-1 的同构改动已在两个
FATE 样片上复验：唯一图 6/7、14/15，与软解逐字节相同，仍差末一幅
（见 [vc1-drain.md](../evidence/p6-2026-11-15/vc1-drain.md)）。详见
[drain-eos.md](../evidence/p6-2026-11-15/drain-eos.md)。
2026-11-15 该修复以 v0.2.0 运行包部署到在役机：MPEG-2 参考流由 88 帧恢复
为 90 帧、99% 像素与软件参考相同，H.264/HEVC 解码与 H.264/JPEG 编码回归
通过（见 [v020-deploy.md](../evidence/p6-2026-11-15/v020-deploy.md)）。
2026-11-16 在 v0.2.0 运行包上跑满 30 分钟持续负载：545 轮、0 失败，HEVC
30/30 与 H.264 300/300 逐帧比对全部匹配，CMA 与可用内存无单调下降
（见 [soak-30min-v020.md](../evidence/p6-2026-11-15/soak-30min-v020.md)）。
随后把窗口扩到 2 小时：2205 轮、0 失败，66150 帧 HEVC 与 132300 帧 H.264
逐帧哈希全部匹配，CMA 与可用内存无下降趋势，dmesg 无警告
（见 [soak-2h-v020.md](../evidence/p6-2026-11-15/soak-2h-v020.md)）。
此前 11-15 那次跑到 191 轮被外部复位截断；过夜验证仍待补做，且服务共存
一项要等 USB 磁盘恢复后才能覆盖
（见 [outage-2026-11-15.md](../evidence/p6-2026-11-15/outage-2026-11-15.md)）。

每阶段基本回归覆盖 H.264/HEVC 三类有效样片、JPEG、旧 codec smoke、
1080p B 帧并发、固件错误与新会话恢复、模块/Overlay 卸载。初期短测试
通过后运行 30 分钟持续负载，再逐步扩大到 2 小时及受监控的过夜验证。
负载/码率按 P0 能持续完成的配置设置，有界输出、期限和清理自己的文件。
长时测试发现退化则缩小复现，不能持续影响在役服务。

记录五项服务状态及可检查的功能入口、温度、CPU、CMA/内存回收、时间戳
连续性、完整帧数、内容抽查和新增内核日志。长测试内容抽查不能替代短样片
逐帧完整比对，所有报告明确各自覆盖范围。

每个独立变更按 Conventional Commits 提交，同步 additive 补丁、双语
README、使用/验收说明和 CI；CI 使用对应 head。硬件报告附源码 commit、
模块/固件/工具哈希。阶段完成可交付独立校验包；编码主线和集成验收通过后
准备 v0.2.0 预发布草稿，按[发版流程](release.md)审阅，旧 v0.1.0 不改写。

当前主线移植、静态 DT/共享 power-domain 与公开 RFC 放在上述功能和
稳定性之后。2026-11-16 完成主线编译级移植：`patches/research/` 以 v7.3.4
为基准，模块、全部 ARM DTB 与 binding 检查通过，实机验证仍缺
（见 [移植记录](../evidence/mainline-2026-11-16/PORT.md)）。2026-11-16 又把
共享 power-domain 的 AO 部分实现为 `patches/research/0004..0008`：Meson8b
VDEC 域进入 genpd，驱动改为运行时引用并在无域时回退到原 AO 直写，
`amlogic,ao-sysctrl` 随 `power-domains` 的有无变成条件必需，DT 节点改用域
phandle。当时九个补丁按序应用且 `checkpatch --strict` 干净，模块与 pwrc 无警告
编译，六个 Meson8/8b/8m2 DTB 通过 schema 校验，负例（去掉域又不给 AO
sysctrl）按预期报错。2026-11-16 又实现共享 DOS 那另一半为 `patches/research/0009..0012`：
`amlogic,meson8b-dos` syscon 拥有该窗口，驱动经 `amlogic,dos` 用 `regmap_mmio`
访问并在无 syscon 时保留自有映射，位操作在 syscon 下改为单次加锁的
read-modify-write，binding 只在缺 phandle 时要求两段 reg。十三个补丁按序
应用、`checkpatch --strict` 干净，模块无警告编译，ODROID-C1 DTB 拆出 syscon
节点，GXBB/GXL/G12A/SM1 的 DTB 在改动后的 binding 下仍通过。实机行为仍未
验证，上游也没有编码器消费该窗口（见[方案](power-domain-design.md)）。
2026-11-16 再补上最后一个功能性缺口 `patches/research/0013`：Meson8b 采集
字节序转换。每个采集 buffer 拥有一块按固件字节序的私有 canvas 块，完成时经
缓存别名转换进待出队的 buffer；NV12M canvas 的 endian 设为 0。每块多占
1.5 倍图像大小的 CMA，因此采集 buffer 上限降到 12、VIFIFO 降到 4 MiB 以适配
64 MiB CMA。十四个补丁按序应用、`checkpatch --strict` 干净，模块无警告编译且
可由 pristine 树逐字节复现，主机测试锁定平面切分与字交换的自逆性。
STREAMON 不再拒绝，但实机行为、拷贝开销与 buffer 预算均未验证。
2026-11-16 另加 `patches/research/0014`：字交换在调用方允许时走 NEON。
arm32 不允许 `kernel_neon_begin()` 与 NEON 代码同处一个编译单元，故主体单独
成文件并用 `CC_FLAGS_FPU` 编译，调用方保留标量循环，由 `may_use_simd()`
选择；`<arm_neon.h>` 经内核的 `<asm/neon-intrinsics.h>` 引入，否则 `intptr_t`
与 `linux/types.h` 冲突。十五个补丁按序应用、`checkpatch --strict` 干净，模块
无警告编译，NEON 指令只出现在为该编译单元生成的目标文件中，主机校验锁定其
与 `__builtin_bswap64` 等价；驱动内的实际收益仍未测量。公开 RFC 仍
待提交。重启验收需具备实际可恢复启动条件，再开展；不把 runtime 启停
通过算成重启验收。HEVC Main10/tiles、4K/B 帧编码、多编码会话与其他无
