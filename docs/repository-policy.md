# 仓库内容与验证记录规则

Git 保存可维护的源码、构建输入和精简结论。运行过程产物独立归档，不能
以“保留证据”为由持续堆入源码仓库；日期目录也不构成例外。

| 内容 | 保存位置与要求 |
| --- | --- |
| 驱动、构建/运维脚本、自动回归 | 正式源码目录；脚本必须可复用，不能绑定某次部署的地址、路径或状态。 |
| 固件与来源、依赖锁定 | `firmware/`、`baseline/`、`config/`；保留固定来源、许可和校验信息。 |
| 最小测试素材和预期结果 | `tests/fixtures/` 或 `samples/`；必须有实际测试用途、来源/生成方式和许可。输出视频不能仅因可解码而成为 fixture。 |
| 能力、部署、历史故障与验收结论 | `docs/validation.md`、`docs/rollout-status.md`、`docs/validation-records.md`；保留版本、输入范围、方法、结果与未验证边界。 |
| 日志、逐帧明细、报告 JSON、输出视频、截图、CI 状态快照、试验脚本和草稿 | 忽略的 `build/reports/`；有长期价值的原件复制到工作区外的归档存储。 |
| 生产备份、登录材料、原始故障现场 | 工作区外私有归档，或忽略的 `private/`；禁止提交到公开 Git。 |

`evidence/` 已退役，全部历史内容移出当前 Git 树。不得重建日期证据目录、
通过 `git add -f` 绕过忽略规则，或改名为 `docs/evidence`、`reports` 等继续
提交相同流水账。旧阶段计划和运行记录只提炼有持续价值的结论，不逐文件
搬进 `docs/`。历史结论必须保持原始时间和版本，不继承到新构建。

## 一次开发或硬件验证结束后

1. 让测试/构建输出写入 `build/`，按需将本次报告放在
   `build/reports/<topic>/`。该目录可清理，不是备份。
2. 将有效回归提升为 `tests/` 中可自动执行的测试；临时实验代码仍留在报告目录。
3. 更新相关正式文档的结论和限制。硬件报告摘要至少记录内核/板型、驱动提交、
   模块哈希、工具与样片来源、完整帧数/内容、错误恢复、服务和回退结果。
   构建成功、节点出现和退出码不能替代这些验证。
4. 需要复核的原件制作 SHA256 清单并校验归档，记录报告标识、对应源码和
   保存期限。长期留存使用独立机器/备份盘；CI artifact 的短期保留不够。
   有可用的永久公开附件时，摘要链接该附件并记录哈希；没有则明确说明
   原件仅在本地保留，不伪造可下载入口。
5. 提交前检查 `git diff --cached --stat` 和 `make test`。新 clone、CI 和源码包
   不得依赖本地报告、私有归档或历史临时目录。

`scripts/check-docs.py` 在 `make test` 中拒绝被跟踪的退役/生成目录和日志，
并拒绝正式 Markdown 链接到这些本地目录。审核还应检查文件的用途，避免
把逐次 JSON/截图/视频移动到另一个路径后绕过规则。

## 历史清理与留存

2026-11-23 清理以 `bd47ef80f2434fc4124368c1bcae7c32cbcd9509` 为基线：
428 个 `evidence/` 文件和 21 个已跟踪的 `private/` 文件全部取消跟踪；
旧开发日志/阶段计划先归档，再以正式摘要替代。全部原件、清单和已有 Git
refs 的 bundle 在工作区外完成逐文件校验，实际位置记在忽略目录供本机恢复。
提交前脱敏复核又移除了 28 个绑定旧生产部署路径的历史试验脚本，原件同样
校验后独立归档。可复用的正式测试和通用运行包加载器继续保留。

公开文件只使用通用安装路径、文档示例主机名和保留测试地址；禁止写入真实
设备 IP/MAC/Tailnet 名称、登录凭据、访问令牌或本机备份/归档绝对路径。
提交前检查最终文件内容及新增行，原件和脱敏检查报告放在忽略目录。

旧提交/标签未改写，因此旧 Git 对象仍可能包含这些材料。此次清理让新的
源码树和未来源码包不再携带它们，不缩减已存在的 Git 历史对象。修改公开
历史和标签是独立迁移，不能混入日常文档清理。已发布包也不会被覆盖。

恢复和备份要求见[工作区迁移](workspace-migration.md)；精简历史结论见
[验证记录](validation-records.md)和[研究线验证](research-validation.md)。
