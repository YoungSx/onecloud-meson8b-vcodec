# S805 厂商能力追平

目标分为格式、内容、标准接口、数据路径和吞吐。固定厂商源码为 Hardkernel
`5aed95d35d252cafc75ce613a3a0052285662de2`；不把其他 Meson 芯片的实现
当作 S805 能力。迅雷出厂固件的配置与同机基准尚缺，当前唯一设备为在役
WanOS，无备用板/串口。新增硬件路径先完成工作机实现和边界/构建检查，
保持未部署；不修改启动文件或用生产持续压力替代取证。

## 当前执行顺序

1. 性能拆分；GE2D 字节序/缓冲自检通过后，继续裁剪、NV12 缩放和 DMA 生命周期。
2. HEVC tiles，覆盖均匀/非均匀、slice、MV 与滤波。
3. H.263、WMV3 等有固件依据的格式，再处理 MPEG/VC-1 完整性。
4. 单 HCODEC 多会话调度及资源预算；严格区分实例数与总吞吐。
5. 对相同输入、质量、内存条件完成厂商路径与移植的硬件内容/性能对照。

历史 H.264 #5 调查保持开放，按用户选择暂停主动复现。没有适用于 S805 的
HEVC 编码、Main10 或可靠高级 H.264 编码路径时，不添加虚假的能力枚举。
AVS 标准 UAPI/应用落点、WMV3 Annex L/RCV 封装也必须明确后再开放格式。

HEVC tile 几何遵守 H.265 均匀分区，例如 30 CTU/4 列为 `7/8/7/8`，
不复制厂商旧 `7/7/7/9`。RPM 的非均匀宽/高按厂商值读取，最后一列/行由
图像总尺寸推导；微码参数与真实 slice 内容仍需要 S805 样片验收。
SAO scratch 保留厂商的整图大小/基地址协议，按列/行检查容量；不把仅有
源码计算的 tile scratch 地址写成一个未经验证的新协议。

WMV3 前缀参考固定
[`libamcodec 4eebd67b142837fbb418abf5390060d4639440ba`](https://github.com/osmc/libamcodec/blob/4eebd67b142837fbb418abf5390060d4639440ba/amplayer/player/player_hwdec.c#L598)
及同树 `player_av.c` 的逐帧前缀。独立重写有界协议转换，不搬入播放器或
有全局状态/未检查缓冲的 VLC 实现。H.263 同树的 `h263vld()` 确认主机
解析/VLC/反量化是固件输入协议的一部分；当前已补入该层，每幅重置运动
预测，各会话独立保存PLUS头，检查输入位和输出字节边界。标准码表取自 FFmpeg n7.0.2
`h263data.c`，原 LGPL-2.1+ 码表按第3节转为 GPL-2.0+，保留来源声明。
初始 H.263 草稿仅喂原始 ES 的路径已修正，不作为可用能力交付。

H.263自定义尺寸按32×32至1920×1080、4像素步进协商，宏块按向上取整
处理；图像尺寸必须与会话一致，不提供流内尺寸切换。UFEP=0只继承本会话
成功转换的PLUS头，截断/容量/尺寸失败不会更新它。时钟按标准区分UFEP=1
的8位参数与每幅2位扩展TR，官方FFmpeg软解验证过续帧改写后的三图哈希。
运动预测行保存在会话堆内存，主机覆盖1916×1080及GOB行号边界；该尺寸
检查不证明HD硬解。PB/B、UMV、AIC、算术编码等可选工具仍明确拒绝，
转换输出保留1 MiB及OUTPUT缓冲容量限制；无法容纳时返回错误。

## HEVC 参考状态

当前源码按有符号POC判断低延迟：当前0/参考-1为过去引用，当前-1/参考0
为未来引用，保留寄存器上的32-bit POC表示。temporal-zero基准按H.265
排除TRAIL_N/TSA_N/STSA_N及RADL/RASL；例如基准0之后的前导POC -7不更新
基准，下一POC 4保持4，不被错误算成-12。实际函数14,976组POC/基准输入
与固定FFmpeg 7.0.2算法一致，另覆盖B列表和MPRED低延迟位。

固定S805厂商[源](https://github.com/hardkernel/linux/blob/5aed95d35d252cafc75ce613a3a0052285662de2/drivers/amlogic/amports/vh265.c#L3177)
把LongTerm_Curr/Col/Ref设为0并标TODO；不能以LT寄存器存在作为完整协议
依据。当前短期参考路径显式清零HEVC_MPRED_LT_REF，与厂商已实现路径一致。
这不新增长期参考支持，也不证明芯片做不到；长期RPS/POC和固件输出仍缺
可验收的同芯片依据。此次仅主机/ARM检查，未部署，无前导图片实机验收。

当前RPM校验在每个slice上检查POC位数、参考数/列表标志、slice类型、merge
字段及布尔标志，先于几何快速返回；后续slice和空几何通知不能跳过这些
后续POC/MPRED仍使用的字段。实际函数回归覆盖正常独立/依赖slice及损坏
字段拒绝。S805最大12槽与12块MV区域匹配，1920×1088在16/32/64 CTU下
每槽最多261120字节，小于262144字节；实际地址函数覆盖所有槽和尾CTU。

MC引用列表当前先解析全部条目再写表，避免缺失图片被跳过后压缩硬件索引；
P/B所需列表为空、引用缺失/未保留、自引用及越界槽均返回错误。启用TMVP
时必须有有效collocated图片；I slice显式重设占位指针，后续slice同步当前
类型。错误向slice处理传播，停止MC/MCRCC/MPRED/SAO和固件继续请求。
这些主机引用回归不证明损坏流恢复或正常多引用图片已通过实机。
地址预算检查不证明MV内容、DPB选择或多slice实机完整性。

DPB预算当前纳入会话内已接收SPS的最大声明，保留原重排余量；例如零重排
而DPB为10时，池需求不再停在6。输入预读取到较小参数集不会降低该上界。
容量增长在图片头处理处追加槽和地址表，正常同几何增长保留旧引用；仅
预算变化不交付伪造LAST或发分辨率事件。该上界可能提前为尚未激活的SPS
占用CMA，直到新会话；分配失败中止队列。低延迟多引用及并发内存仍未实机。

## 显示区域与像素比例

当前源码接入只读G_SELECTION和CROPCAP，修复缺失selection注册及拒绝内核
归一化CAPTURE类型的问题；主机使用原Linux 5.15.79核心函数验证两种类型。
CROP报告源裁剪，COMPOSE报告从原点开始的已裁剪CAPTURE区域，未解析出
独立coded尺寸时bounds回退到协商尺寸；精确输入coded边界仍需逐格式验收。
新会话清除旧coded/crop状态，保持尺寸切换时的几何回退。

MPEG-4/VC-1按厂商PIC_RATIO解码各自有效码表和扩展比例，未知/零分母回退
1:1；H.263保留baseline 12:11、PLUS自定义比例和UFEP继承，失败转换不更新。
H.264复用原码表并验证原映射行为。内部保存SAR x/y，CROPCAP按规范返回y/x。
官方FFmpeg 7.0.2的直接复制方向错误已通过真实函数复现，并独立放入既有
可选bug修复流程；见[FFmpeg边界](ffmpeg-compatibility.md#bug-修复--bug-fixes)。
这些检查没有硬件像素、尾帧或显示验收，不证明旧格式完整性问题已修复。

编码端新增标准SAR控件、四项cluster事务和SPS写入，保留crop/色彩/帧周期；
默认关闭，流内改变返回EBUSY。IDC菜单17转换为NAL的255，扩展字段为
1–65535。主机及原版ARM工具的正常/扩展比例12图检查通过；65535/1软件
样本出现2/12并保留失败。源码、工具与边界见[编码SAR](ffmpeg-compatibility.md#编码-sps-像素比例)。

## AVS 接口缺口与旧格式边界

AVS JiZhun 的 S805 固件和厂商帧协议存在，不属于已证明的硬件缺失。
本轮再次核对 Linux 5.15.79 UAPI 及主线固定提交
[`b6a9fa34ce4187cb69d3c588a4bbffc31ce5db8f`](https://github.com/torvalds/linux/blob/b6a9fa34ce4187cb69d3c588a4bbffc31ce5db8f/include/uapi/linux/videodev2.h)，
均没有 AVS 压缩 FOURCC；官方 FFmpeg 固定提交
[`4155ce3d4a18cfa01112db57bcfcac6e1db8de30`](https://github.com/FFmpeg/FFmpeg/blob/4155ce3d4a18cfa01112db57bcfcac6e1db8de30/libavcodec/v4l2_fmt.c)
的格式映射和 M2M decoder 表也没有 AVS。继续推进需单独定义可维护的
标准 UAPI/应用落点，不能借用 MPEG4/VC1 标识，不能把 AVS2/AVS3 当成 AVS
JiZhun。当前不开放该格式，完整追平目标仍未完成。

旧格式 IRQ handler 已纠正一个确定的错误边界：MPEG-1/2 的1–8、
MPEG-4/VC-1/MJPEG的1–4固件槽号先验证再转换为零起始索引。旧取模行为会
把9或5之类越界通知别名到有效图片；当前错误通知终止队列并清邮箱，不交付
或回收错误槽。实际 handler 主机回归覆盖正常、空通知、越界和零槽状态。
这没有证明历史尾帧/B图损坏由同一机制引起，不能替代逐帧硬件对照。

## 旧格式验图入口

当前 [m4v-frame-compare.py](../scripts/m4v-frame-compare.py) 的 raw canvas 模式
按驱动实际32字节行宽/高度对齐及64 KiB平面容量读取，覆盖854×480等非64
倍数宽度；旧64字节布局必须显式 `--canvas-align 64`。参考为 `yuv420p`，
`--ref-format nv12` 可读取交错参考。所有raw输入必须包含完整帧，空输出、
截断、乱序、少/多帧均失败；每幅匹配后检查全部可见Y/U/V像素，输出各平面
MAD/PSNR，`--max-mad` 限制每平面的平均绝对误差（默认2）。图案签名仅用于
身份诊断，signature-only输出会标明未检查像素；不作为图片内容验收。

```sh
python3 scripts/m4v-frame-compare.py hardware.nv12 software.yuv \
  --size 854x480 --canvas --bands 16 --max-mad 2
```

[MPEG-2顺序诊断](../scripts/m2v-frame-order.py)也使用同样canvas布局与完整帧
检查；相邻像素相同的图片优先保留原位置匹配，避免误报乱序。其每4个亮度
样本检查属于局部顺序诊断，不替代上面的全平面检查。

主机回归复现并纠正三个旧工具缺陷：反向帧序和两端空输出错误通过，以及
当前32字节stride被旧64字节读取；同时覆盖色度交换、同均值亮度损坏、
短输出、畸形签名和旧布局。历史记录保留原时间与验证强度，不把工具修复
倒推为某个旧故障的原因，也不据此宣称当前驱动完整解码通过。

## 已部署模块的短时性能快照

2026-11-23 使用当前在役 `3c7d785` codec、原 `5.15.79-meson`/64 MiB CMA，
模块没有切换。固定 1080p 静态彩条、30 fps、60 图（2 s）：

- H.264 硬解→4 Mbps H.264 硬编，完整软解为 60/60，命令墙钟约 4.052 s，
  约 0.494×；转换累计 558 ms，输入拷贝 248 ms，无 DMA-BUF 直读。
- null 输出下，FFmpeg 内部解码耗时 1.653 s、60 图；命令总墙钟 2.366 s。
  加 `scale=1280:720` 后，内部耗时 5.023 s、60 图，命令总墙钟 5.882 s，
  子进程 CPU 约 7.369 s。输出完整计数不代替像素/质量验收。
- 原始视频写入 tmpfs 的对照为 10.008/7.393 s，包含 rawvideo 编码与 I/O，
  不用于硬件吞吐判断。转换计数约 7–14 ms/帧，负载差异明显。

这些是同一静态源的有界测量，没有音频/HLS，也非满吞吐、画质比较或新的
稳定性验收。缩放 CPU 开销有直接测量依据，GE2D 优先验证该收益；不能从
计数相加预测实际加速。原件在忽略报告目录，当前没有永久公开附件。

工具入口见[阶段测量](performance.md)，精确已安装来源见[部署快照](rollout-status.md)。
